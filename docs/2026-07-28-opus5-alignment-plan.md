## 0. このドキュメントの使い方

このファイルは、`~/skills` で作業するエージェントへの指示書です。会話コンテキストを持たない状態で読まれる前提で書いてあります。

作業対象は以下の 4 スキルと、それを説明する 2 つの USAGE ファイル:

- `subagent-orchestration/`
- `design-impl-docs/`
- `implement-review-loop/`
- `code-review-agent/`
- `USAGE.md` / `USAGE.ja.md`（内容は同一の英日対訳。**片方だけ直さない**）

`commit-workflow` / `ts-type-safety` / `neverthrow-*` / `function-signature-typing` / `ai-friendly-lint-rules` は今回の対象外。触らないこと。

## 1. 背景 — なぜ削るのか

これらのスキルは Claude Opus 4.8 以前を前提にチューニングされている。Opus 4.8 は「委譲を渋る」「検証を省く」傾向があったため、それを補う方向（＝指示を足す方向）で設計された。

Opus 5 では前提が逆転した。公式ガイドから該当箇所を引く:

> Claude Opus 5 は、指示されなくても自身の作業を検証します。プロンプトに明示的な検証指示（「自明でないタスクには最終検証ステップを含める」「サブエージェントを使用して検証する」）が含まれている場合は、削除してください。このような指示は Claude Opus 5 で過剰な検証を引き起こし、削除することで品質を損なうことなく無駄なトークンを削減できます。

> Claude Opus 5 は、以前のモデルよりも積極的にサブエージェントに委任します。委任は、真に独立した大規模な作業の流れでは効果を発揮しますが、小さなタスクに適用するとコストと時間が倍増します。

> レビュープロンプトに「重大度の高い問題のみを報告する」や「保守的に」と書かれている場合、モデルはその指示を文字通りに従って報告を減らす可能性があります。代わりに、すべてを報告させて別のパスでフィルタリングするよう依頼してください。

> Claude Opus 5 は、デフォルトかつ最大値として 100 万トークンのコンテキストウィンドウを持ち、指示の遵守、ツール呼び出し、推論はウィンドウ全体を通して一貫性を保ちます。

出典: https://platform.claude.com/docs/ja/build-with-claude/prompt-engineering/prompting-claude-opus-5

**重要な注意:** これは「ルールを減らせば良い」という話ではない。削るのは**不要になった命令**であって、**判断に必要な事実**ではない。迷ったら「これは Opus 5 が指示なしでやることか？」で判定する。Yes なら削除、No なら残す。

## 2. 共通方針 — 単一 source of truth

現状、同じルールが複数ファイルに実体としてコピーされている（実測値）:

| ルール | 実体の出現箇所 |
|---|---|
| 中核ルール（impl.md 書き込み → doc review 必須） | `design-impl-docs` ×4 / `subagent-orchestration` ×2 / `implement-review-loop` ×1 / `USAGE.ja.md` ×3（英語版含め計 13） |
| 50% ルール・コンテキスト使用率の自己申告 | `code-review-agent` ×7 / `subagent-orchestration` ×3 / `implement-review-loop` ×2 = 12 |
| エスカレーションプロトコル | `subagent-orchestration` に本体、`implement-review-loop` に部分再掲 ×3 |

**以降の全作業に適用する原則:**

- 1 つのルールの**実体は 1 ファイルだけ**に置く。他所からは「〜スキルの〈節名〉に従う」というポインタのみにする
- ポインタは節名で参照する。行番号で参照しない（ずれる）
- 削除するルールは、全出現箇所を一度に消す。1 箇所だけ直して他を残すと、後から読んだエージェントが古い方を拾う

各ルールの正典（canonical）配置は下記の通りとする:

| ルール | 正典 |
|---|---|
| エスカレーションプロトコル | `subagent-orchestration` |
| 委譲の判断基準 | `subagent-orchestration` |
| 役割別エージェント定義 | `subagent-orchestration` |
| design.md / impl.md の内容と更新契機 | `design-impl-docs` |
| ループ手順・停止条件・反復上限 | `implement-review-loop` |
| レンズ定義・採点・閾値 | `code-review-agent` |

USAGE.md / USAGE.ja.md は「全体像の案内」であり、ルールの実体を置く場所ではない。手順の要約は持ってよいが、各スキルの規約文をコピーしない。

**grep の落とし穴:** 日本語リテラル（例: `grep -rn "中核ルール"`）だけでは実体を取りこぼす。以下は語句を含まないまま実質コピーになっている:

- `implement-review-loop/SKILL.md` の description — ルール本体の要約がほぼ全文入っている
- `design-impl-docs/SKILL.md` の実行手順 — upfront 作成ルールの実質コピー
- `USAGE.md`（英語版）— 対応する英語表現（"core rule" など）
- `USAGE.md` / `USAGE.ja.md` の依存関係表の「前提」列

**`SKILL.md` の description は全セッション常駐する**ので、§2 の原則（実体は 1 箇所）が最も強く効く場所。ここに本文の要約を置かない。

### 項目 1 — 「規模の大小を問わず委譲」の撤回【最優先】

**対象:** `subagent-orchestration/references/rules.md`（「役割分担」節、現状 19 行目付近）、および `subagent-orchestration/SKILL.md` の description / TRIGGER 行

**現状:**
> 規模の大小を問わず委譲する。小さいタスクでも直接実装しない。

**問題:** Opus 5 は放っておいても委譲しすぎる。この一文はアクセルの上にアクセルを重ねている。1 ファイル 3 行の修正に実装エージェント → lint → doc review → 5 レンズ + Haiku 採点 → コミットエージェントが起動する。

**変更後の意図:** 「必ず委譲」から「委譲すべき場面の判断基準」に置き換える。基準の要点:

- 委譲する: 真に独立していて並列化できる大きな作業（広い複数ファイル調査、独立した複数モジュールの実装など）
- 委譲する: 中間出力が大量に出る作業（結論だけをメインに返させたいもの）
- 委譲する: author != reviewer を担保する必要がある作業（コードレビュー・ドキュメントレビュー）
- **委譲する（例外扱い）: git 書き込み操作。** これは効率ではなく**権限境界**の問題なので、規模を問わず例外なくコミットエージェントに委譲する。この一文を必ず入れること — 「小さい作業は委譲しない」を一般則として書くと「1 行の typo 修正だからコミットも自分でやる」という読みが通ってしまう
- 委譲しない: 自分の作業の検証・ダブルチェック目的
- 委譲しない: 委譲プロンプトを書くコストが作業そのものを上回る作業
- 1 体で足りるなら 1 体にする。起動数を抑える

**ユーザー判断済み（2026-07-28）— オーケストレーターの直接編集を許可する:**

「委譲しない」に **「単一ファイル・数行に収まり、仕様判断を伴わず、lint / typecheck で検証が閉じる修正はオーケストレーターが直接編集してよい（境界を超えたら実装エージェントに委譲）」** を含める。

これはスキルの自己定義の変更なので、以下も併せて直す（初版は見落としていた）:

- `subagent-orchestration/SKILL.md` の「目的」節「作業はすべて専門サブエージェントに委譲する」
- `USAGE.md` / `USAGE.ja.md` の Mermaid 図ノード「・自分ではコードを書かない」

**注意:** `SKILL.md` の description は全セッションのコンテキストに常駐する（スキル一覧として読み込まれる）ため、ここに「規模の大小を問わず適用する（小さい修正でも委譲する）」が残っていると本文を直しても効果が出ない。**両方直すこと。**

**波及:** `USAGE.md` / `USAGE.ja.md` の該当記述、`implement-review-loop` に委譲前提の記述があれば整合を取る。ただし `implement-review-loop/rules.md`「なぜこのループか」の「実装エージェントは自分の書いたコードも客観視できない」は author != reviewer の根拠なので**削らない**。

### 項目 2 — レンズの抑制文言を削除

**対象:** `code-review-agent/references/rules.md` の Lens 3・Lens 5 の委譲プロンプト雛形

**現状（削除対象）:**

- Lens 3: 「『なんとなく気になる』レベルは含めない。明確な失敗シナリオを示せる指摘のみ挙げてください。」
- Lens 5: 「単発の『好み』レベルの命名 bikeshedding は挙げないでください。」
- Lens 5「拾わないもの」内: 「命名の細かい bikeshedding（明確に意味を損ねている場合のみ挙げる）」

**問題:** このスキルは「全件報告 → Haiku 採点 → 閾値 80 でフィルタ」という役割分離を採用しており、これは公式ガイドの推奨と一致している。ところが個々のレンズ側にも抑制指示が入っているため、**フィルタが二重にかかっている**。Opus 5 は抑制指示を文字通り守るので、レンズ側で recall が落ち、閾値に到達する前に候補が消える。

**変更後の意図:** レンズ側に残すのは「**観点の分離**」だけにする（＝他レンズの担当領域は挙げるな、という重複排除）。**強度の抑制はすべて Haiku 採点側に寄せる。**

**残すもの（削除しないこと）:**

- 「〜は別レンズが見ます」系の観点分離指示 → 残す
- 「共通 False Positive リスト」節（linter が catch する系 / pre-existing / 意図的に silenced されているもの等）→ **残す**。これは強度抑制ではなく観点の重複排除なので、今回の対象外
- Lens 3 の「拾うもの」列挙 → 残す

**判断に迷ったら:** その一文が「何を見るか」を定めているなら残す。「どれくらい厳しく言うか」を定めているなら削る。

**併せてやること:** レンズ側に抑制が再導入されないよう、「Confidence Scoring」節に「強度のフィルタはこの採点段階に集約する」旨を 1〜2 文で明記する。また「なぜこの構造か」節が挙げる構造の動機のうち「主観の混入 — 『なんとなく気になる』レベルの nitpick が並ぶ」は、レンズ側抑制の根拠に読めるので「これは採点 + 閾値で潰す」と書き換える。

**副作用（許容する）:** 抑制を外すと候補件数が増え、Haiku 採点は指摘 1 件 = 1 エージェントなので採点コストが比例して増える。閾値 80 が単独でフィルタを担うことになるため、変更後は閾値の妥当性を手動で確認する（`code-review-agent` には eval が無い。§5 参照）。

### 項目 3 — doc review の起動契機を絞る（※初版から方針変更）

**対象:** `design-impl-docs/references/rules.md`（「中核ルール」節、および「更新のタイミング」表）、`subagent-orchestration/references/rules.md`（「ドキュメント連携」節・「ドキュメントレビューエージェント」役定義）、`implement-review-loop/references/rules.md`（前提・step 3a）+ `SKILL.md`、`USAGE.md` / `USAGE.ja.md`

**現状:** `impl.md` に書き込みが発生するたびに、author とは別エージェントによる doc review を必ず走らせる。upfront 作成時もループ内の毎周も対象。

**初版の記述が誤りだった点:** 初版はこう書いていた —

> 実害は「次のエージェントが古い方針を読む」ことだが、それは code review の Lens 2（内部整合性）が既に拾う設計になっている。

これは事実誤認。`code-review-agent/references/rules.md` の Lens 2 委譲プロンプトには **「design.md は参照しません」** と明記されている。レンズの担当は以下で、**design.md ↔ impl.md を突き合わせるレンズは存在しない**:

| | 突き合わせ対象 |
|---|---|
| Lens 1 | design.md ↔ **コード**（「外部から観測できる振る舞い」限定、impl.md は参照しない） |
| Lens 2 | impl.md ↔ **コード** |
| doc review | design.md ↔ **impl.md** ← 誰も代替しない |

doc review の 5 category との照合結果:

| category_hint | code review でカバーされるか |
|---|---|
| 記述漏れ / 記述過剰 | 部分的に Lens 2 |
| **仕様乖離**（impl.md の技術的判断 vs design.md の仕様） | ❌ 誰も見ない |
| **未決先取り**（design.md の未決事項を impl.md で実装済み扱い） | ❌ 誰も見ない |
| **履歴不整合**（旧仕様の記述が impl.md に残存） | ❌ 誰も見ない |

**さらに因果が逆だった。** docs → code の sequential を採用している理由は「Lens 2 が信頼できる `impl.md` を要求するから」。毎周の 3a を外すと Lens 2 は drift した `impl.md` をリファレンスに走ることになり、**Lens 2 の精度が落ちる**。「3a が Lens 2 を支えている」関係であって、その逆ではない。

**変更後（ユーザー判断済み・2026-07-28 — 「案 B: 起動契機を絞る」を採用）:**

doc review を走らせる契機を以下に限定する:

- **upfront 作成時** — 例外なく必須。author ≠ reviewer もここは維持する。方針を丸ごとロックする瞬間であり、公式が肯定する「ライター・ベリファイアーパターン」に該当するので削らない
- ループ内で `impl.md` の **「構成」「技術的判断」** セクションに書き込みが発生した周
- 直前に **design.md が変更された** 周の `impl.md` 更新（内容を問わず）

**skip してよいのは:** 「実装状況」のステータス更新のみの周、「レビュー指摘と対応」への追記のみの周。これらは方針を動かさないので、drift しても下流のリファレンスを誤らせない。

実際の削減幅は大きい（初回以降の多くの周は実装状況 + レビュー指摘の更新のみ）。一方でカバレッジホールを作らず、2026-07-24 のユーザー指示（「作成 or 編集とレビューはセットに」）の趣旨も保つ。

**変更後のルール文に必ず残すこと:** 「なぜ code review で代替しないか」= 上記のレンズ担当表の要約。これを書かないと、次に読んだエージェントが同じ誤解（「Lens 2 が拾うから doc review は冗長」）に到達して撤廃を再提案する。

**memory の更新が必要:** `feedback-impl-md-review-pairing`（`~/.claude/projects/-Users-konoreiji-skills/memory/`）は「`impl.md` に書き込みが発生するたび」と書かれており、本項目の適用後は不正確になる。案 B の内容に更新する。

**波及が広いので注意:** 「中核ルール」は 4 ファイル 13 箇所に実体がコピーされている。項目 0 でポインタ化を済ませてから着手すること（未実施なら `grep -rn "中核ルール" --include="*.md" .` で洗い出す。ただし `*/workspace/` 配下は eval の出力なので対象外。§2 の「grep の落とし穴」も参照）。

### 項目 4 — 50% ルールとコンテキスト使用率の自己申告を撤廃

**対象:** `subagent-orchestration/references/rules.md`（「サブエージェントのコンテキスト管理」節）、`code-review-agent/references/rules.md`（5 レンズすべての委譲プロンプト雛形 + 実行制約節）、`implement-review-loop/references/rules.md`

**現状:** サブエージェントのコンテキスト使用率が 50% に達したら新規エージェントに切り替える。判定は「成果物末尾に自身のコンテキスト使用率（概算でよい）を必ず含めよ」という自己申告方式。

**問題は 2 つ:**

1. **閾値の根拠が失われた。** Opus 5 は 100 万トークンウィンドウ全体で一貫性を保つと公式が明言している。Opus サブエージェントで 50%（＝ 500k）での強制切り替えは、引き継ぎドキュメント作成コストの方が高い
2. **自己申告が機能しない。** モデルは自分のコンテキスト使用率を観測できない。返ってくるのは推測値であり、それに基づく切り替え判断は意味を成さない。しかもこの一文が 5 レンズ全部にコピーされているので、毎回 6 個の無意味な数字が返る

**変更後:**

- **削除:** 「成果物末尾にコンテキスト使用率を自己申告せよ」という指示（全 12 箇所）。委譲プロンプト雛形からも、返却フォーマット（`context_usage` フィールド）からも消す。**返却フォーマットは両側セットで直す** — `code-review-agent/references/rules.md` の「出力形式」スキーマ・「implement-review-loop への引き渡し」項目 4 と、`implement-review-loop/references/rules.md` の受け取り項目は対応関係にあり、文言 grep では片方しかヒットしない
- **削除:** Opus サブエージェントに対する 50% 一律ルール
- **残してよい:** 「compact させず、役目を終えたら新規エージェントに引き継ぐ」という方針と、引き継ぎ方（成果物と未解決事項を明文化 → ドキュメント経由で渡す）。これは判断に必要な事実であって、機能しない機械的閾値とは別物
- Sonnet / Haiku サブエージェントはウィンドウが小さいので、長時間タスクでの切り替えに言及を残してよい。ただし自己申告方式には依存させない

### 項目 5 — 軽い判断を AskUserQuestion に開放

**対象:** `subagent-orchestration/references/rules.md`（「エスカレーションプロトコル」節）

**現状:** 仕様に関わる疑問はすべて design.md 経由。チャットで許されるのはポインタ交換のみ。オーケストレーターの発話は 2 パターンに固定され、「やってはいけない例」が 4 件並ぶ。

**問題:** チャット禁止の理由は 3 つ挙げられているが、うち「選択肢をチャットに貼るとコンテキストを無駄に食う」は 1M ウィンドウで根拠が弱まった。残る 2 つ（単一 source of truth / サブエージェントがアクセスできる）は、**決定を Claude が design.md に転記すれば満たされる**（現ルール自身も「オーケストレーターが転記してから進める」を許容している）。質問フェーズまで design.md 経由に固定する必要はない。

結果として、Yes/No 一つでもユーザーがエディタを開いて書き込む必要があり、往復コストを人間側に押し付けている。Claude Code には AskUserQuestion（選択肢を UI に出して 1 クリックで回答）がある。

**変更後の意図:**

- 軽い判断（選択肢が 2〜4 個、トレードオフが 1 行で書ける）→ AskUserQuestion を使ってよい
- 重い判断（複数論点が絡む、後から根拠を追いたい、決定が後続の複数タスクに影響する）→ design.md 経由
- **どちらのルートでも、決定は Claude が design.md に転記する**（この不変条件は維持する。ここを緩めない）
- **AskUserQuestion は 1 往復上限。** 1 回で閉じない場合（回答が新たな論点を生んだ / 選択肢が想定と噛み合わなかった）は、そこで design.md ルートに切り替える。これを明記しないと、元の痛点だった「チャットで Q&A を繰り返す」に戻る導線ができる

**併せて:** 発話文面を 2 パターンに固定している箇所と「やってはいけない例」4 件は、判断基準に置き換えて圧縮する。Opus 5 は「決定は追跡可能な形で残す」「サブエージェントが到達できる場所に置く」という基準から導出できる。ただし**「ユーザーがチャットで口頭回答した場合、必ず design.md に転記してから進める」だけは明示で残す**（これは判断基準からは導けない運用ルール）。

### 項目 6 — 成果物ドキュメントの長さ制約を追加

**対象:** `design-impl-docs/references/rules.md`（impl.md 節）

**唯一の「足す」変更。** 公式ガイド:

> Claude Opus 5 がディスクに書き込むファイル（レポート、Markdown ドキュメント、要約）は、以前のモデルよりも長くなることがよくあります。

`impl.md` は毎周追記される設計なので、Opus 5 では肥大化が加速する。既存の「コードを読めばわかることを書き写すな」は方向として正しいが、長さそのものへの言及がない。

**追加する内容の意図:** 「実装の現在地が読み取れる最小限に留める。冗長な要約・定型節・埋め草を足さない」。1〜2 文で足りる。長い節を新設しないこと。周ごとの追記で肥大化するので「古くなった記述は追記ではなく置き換えで処理する」も含める。

## 6. 進め方

**順序: 0 → 1 → 2 → 4 → 6 → 3 → 5 → 7。**

- **項目 0 は他項目の前提**なので必ず最初。単独コミットにする
- 項目 3 を後ろに回してあるのは、波及が最も広く（4 ファイル 13 箇所）、他項目と混ぜるとコミットが分離できなくなるため
- コミットは項目単位で分ける（`commit-workflow` スキルに従う）
- **仕様レベルの判断が必要になったら、自分で決めずに手を止めてユーザーに確認する。** 項目 1 の「直接編集を許可するか」と項目 3 の「3a をどう縮小するか」は 2026-07-28 にユーザー判断済み（各項目内に記載）。それ以外で判断が割れる点が出たら止める
- このドキュメントは作業記録ではない。ただし**事実誤認が見つかった場合は訂正する**（放置すると、コンテキストを持たない後続エージェントが誤った前提で作業する）。方針の細かい変遷はスキル本文側に理由を残せばよい
