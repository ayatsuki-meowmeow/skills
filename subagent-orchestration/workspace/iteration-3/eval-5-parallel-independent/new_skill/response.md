# プラン

featureA と featureB は「真に独立していて並列化できる作業」かつ「調査ログという中間出力が大量に出る作業」に該当するため、両方とも調査エージェントに委譲し、同一ターンで 2 体を並列起動する（依存関係が無いので前段の成果を待つ必要はない）。オーケストレーターである自分がやるのは、着手前の design.md / impl.md の存在確認（既知パスの参照＋単発の grep レベルなので自分で直接やる。読み取り系 git コマンドも同様に自分で実行可）、委譲プロンプトの作成、2 体の成果物の検収、ユーザーへの要約報告のみで、コードもドキュメントも自分では書かない。モデルは 2 体とも **Opus**（コードベースの広い読解と制約の抽出が主で、方針が impl.md に落ちるレベルまで固まっていない＝思考が主のタスク）。design.md が存在しない場合は「タスク開始時に確認し、無ければ作成する」規約に従って作成するが、記載すべき現状・制約は調査結果に依存するため、2 体の成果物を受領した後にドキュメントエージェント（Opus）へ 1 体だけ委譲して作成させる（順序: 調査 2 体を並列 → 検収 → design.md 作成委譲 → 報告）。impl.md は今回の依頼が調査までで実装フェーズに入らないため作成しない（実装に進むと決まった時点で、実装着手前に必ず作成する。その書き込みはドキュメントレビューとセット）。今回の依頼は「両方の現状を調査」という範囲が明確で、仕様・要件の選択を含まないため、着手前のユーザー確認は行わず即座に並列委譲する（ここで AskUserQuestion を挟むのは不要な往復）。ただし調査中に仕様・要件レベルの疑問（design.md から答えが出ない選択）が浮上した場合は、サブエージェントには判断させず疑問と選択肢を成果物として返させ、軽い判断なら AskUserQuestion で 1 往復、重い判断なら design.md の「未決事項」経由に載せる。いずれのルートでもユーザーの決定を design.md の「決定事項」に転記してから後続作業を再開する。git 書き込み操作は今回発生しない（調査のみ）。発生させる必要が出た場合も自分では実行せずコミットエージェントに委譲する。最終報告はエスカレーション事項を先頭に置き、featureA / featureB それぞれの現状要約を続ける。

## 委譲プロンプト（役割 / モデル）

### 1. featureA 調査エージェント（調査 / Opus）— 2 と同一ターンで並列起動

> あなたは featureA の現状を調査する専門の調査エージェントです。
>
> **コンテキスト**
> まず以下を読んでください（存在すれば）。存在しない場合は「存在しない」と報告に明記してください。
> - design.md: `docs/design.md`（仕様・要件の source of truth）
> - impl.md: `docs/impl.md`（実装詳細・実装状況）
>
> **タスク**
> featureA の現状を調査し、以下を成果物として返してください。
> 1. featureA に関連するファイルのパス一覧（役割を 1 行で添える）
> 2. 現状の構造（エントリポイント、主要なモジュール／責務の分割、データの流れ）
> 3. 制約（依存ライブラリ、既存の型・インターフェース、テストの有無と範囲、後方互換の要求など変更時に効いてくるもの）
> 4. 未解決の疑問（仕様・要件に関わるもの／技術的なもの を分けて）
>
> 中間の調査ログは返さず、上記の**結論だけ**を要約して返してください。関連ファイルのパスは常に絶対パスで示してください。
>
> **エスカレーション指示**
> 仕様・要件に関する疑問（design.md から答えが出ない選択）に行き当たった場合、**自分で判断しないでください**。「疑問 / 取り得る選択肢 / 各選択肢のトレードオフ / あなたの推奨」を成果物に含めて返し、そこで止めてください。決定はユーザーが行い、オーケストレーターが design.md に記録します。仕様に影響しない技術的な観察（内部設計の妥当性など）は、判断ではなく所見として書いてください。
>
> **境界**
> - コードは一切変更しないでください（調査専門です）
> - ドキュメント（design.md / impl.md）も更新しないでください
> - git 書き込み操作（add / commit / rebase / reset / push など）は一切行わないでください。読み取り系（status / diff / log / show）は必要に応じて使って構いません
> - featureB は担当外です。featureA との接点に気づいた場合は「接点の指摘」として 1〜2 行書くにとどめ、featureB 側の調査には踏み込まないでください
> - 調査の途中で compact が必要になるほど長引いた場合は、そこで打ち切り、得られた成果と未完了リストを明文化して返してください（続きは新規エージェントに引き継ぎます）

### 3. design.md 作成エージェント（ドキュメント / Opus）— design.md が存在しない場合のみ、1・2 の成果受領後に起動

> あなたは design.md を整備する専門のドキュメントエージェントです。
>
> **コンテキスト**
> - design.md: `docs/design.md` — 現時点で存在しないため、新規作成します
> - impl.md: `docs/impl.md` — 今回は作成・更新の対象外です（実装フェーズに入らないため）
> - 前任者の成果物: featureA 調査エージェントの報告 / featureB 調査エージェントの報告（本プロンプトに添付する要約を唯一の入力としてください）
>
> **タスク**
> design-impl-docs スキルの規約に従って `docs/design.md` を新規作成し、featureA / featureB について調査で判明した**現状の仕様・要件・制約**を記載してください。調査で仕様・要件レベルの疑問として返ってきた項目は、「未決事項」節に「疑問 / 選択肢 / トレードオフ / 推奨」の形で置いてください（あなたが答えを埋めることはしないでください）。
>
> 成果物は「作成したファイルのパスと、各節に何を書いたかの要約、および未決事項として立てた項目の一覧」です。
>
> **エスカレーション指示**
> 調査結果だけでは仕様なのか実装の偶然なのか判別できない記述があった場合、断定して書かないでください。「未決事項」に置くか、判断が必要な点として成果物に列挙して返してください。仕様の決定者はユーザーです。
>
> **境界**
> - コードは一切変更しないでください
> - impl.md は作成・更新しないでください（実装着手が決まった時点で別途扱います）
> - 添付された調査要約に無い内容を推測で補わないでください
> - git 書き込み操作は一切行わないでください（コミットが必要ならコミットエージェントの担当です）

## 補足: 今回やらないこと

- **impl.md の作成**: 依頼は調査までで実装フェーズに入らないため作成しない。実装に進むと決まった時点で、実装着手**前**に必ず作成し、その書き込みはドキュメントレビューエージェント（`impl.md` を書いたエージェントとは別体）とセットで実施する。
- **ドキュメントレビューの起動**: 今回 impl.md への書き込みが無いため起動契機に当たらない。
- **コミットエージェントの起動**: 調査のみで未コミット差分が発生しない。design.md を新規作成した場合のコミットは、ユーザーの明示指示を待ってからコミットエージェントに委譲する（「作ったのでついでにコミット」はしない）。
- **検証目的の追加起動**: 調査結果のダブルチェックのためのサブエージェント起動はしない。同じ対象を同じ観点で見せる多重起動もしない（featureA / featureB は観点が実際に独立しているため 2 体）。
