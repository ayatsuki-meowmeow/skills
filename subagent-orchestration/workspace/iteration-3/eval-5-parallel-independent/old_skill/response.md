# プラン

featureA と featureB は依存関係のない独立した 2 機能なので、私（オーケストレーター）自身は一切コードを読まず、調査は 2 体の調査エージェントに分けて**同一ターンで並列起動**します。私がやるのは、着手前の design.md 存在確認（読み取りのみ。`git status` / `git log` 等の読み取り系 git も必要なら自分で実行してよい）、タスク分解、委譲プロンプトの作成、成果の検収、ユーザーへの要約報告だけです。design.md が存在しない場合はまずドキュメントエージェント（Opus）に空の design.md 作成を委譲し、そのパスが確定してから調査エージェントを並列起動します（調査プロンプトに design.md / impl.md のパスを必ず含める必要があるため、この 1 件だけは前段に直列で置きます）。調査 2 件はどちらも「コードベースの広い読解」で判断の余地が大きいタスクなので、モデルは両方 **Opus**。今回は実装フェーズに入らないため impl.md は作成せず（実装に進む段になったら、実装エージェント起動の前に必ず upfront で impl.md を作成し、書き込みと同時に別エージェントのドキュメントレビューをセットで走らせます）、ドキュメントレビューも起動しません。git 書き込み操作は発生しないのでコミットエージェントも起動しません。ユーザーへの確認は、featureA / featureB の「どこまでを調査範囲とみなすか」など仕様・要件レベルの疑問が調査エージェントから返ってきた場合、あるいは私自身が気づいた場合に限り、選択肢・トレードオフ・推奨を **design.md の「未決事項」に書き込み**、チャットでは「design.md の未決事項に判断を記入してください」とだけ伝えて停止します（選択肢をチャットに並べる・「〜という理解で合っていますか」と聞く運用は取りません）。最後に 2 体の成果を検収し、エスカレーション（judgment 待ち項目）を報告の先頭に置いた要約をユーザーに返します。

## 委譲プロンプト（役割 / モデル）

### 1. ドキュメントエージェント（design.md 作成 / Opus）— design.md が存在しない場合のみ起動

> あなたはドキュメント専門エージェントです。design.md（仕様・要件の source of truth）の作成のみを行い、コードは一切変更しません。
>
> コンテキスト: 本タスクの design.md（`docs/design.md`）はまだ存在しません。impl.md も未作成です。ユーザーの依頼は「独立した 2 機能 featureA / featureB の現状調査」で、これから調査エージェント 2 体を並列で走らせます。
>
> タスク: `docs/design.md` を新規作成し、以下のセクション骨格だけ用意してください。中身の仕様を推測で埋めることは禁止です。
> - 概要（依頼内容を 1〜2 行で転記）
> - featureA: 仕様・要件（現時点で未記入である旨のみ）
> - featureB: 仕様・要件（現時点で未記入である旨のみ）
> - 決定事項（空）
> - 未決事項（空。以降オーケストレーターがここに疑問・選択肢・トレードオフ・推奨を追記します）
>
> エスカレーション: 仕様・要件に関わる疑問（featureA / featureB の定義や範囲など）が出た場合、自分で判断して埋めないでください。疑問と選択肢を成果物として返し、判断はオーケストレーター経由でユーザーに委ねます。
>
> 境界: コード変更・impl.md の作成・git 操作は一切行わないこと。design.md 以外のファイルに触らないこと。
>
> 成果物: 作成したファイルパスと、用意したセクション一覧。加えて、**成果物の末尾に自身のコンテキスト使用率（概算でよい）を必ず記載**してください。使用率が 50% に近づいたら、そこまでの成果と未完了リストを明文化して作業を止めてください。

### 2. 調査エージェント A（featureA 現状調査 / Opus）

> あなたは調査専門エージェントです。コードは一切変更しません。
>
> コンテキスト: まず `docs/design.md` と `docs/impl.md` を読んでください（impl.md は未作成の可能性があります。存在しない場合はその旨を成果物に書き、作成はしないでください）。本タスクは独立した 2 機能のうち **featureA** のみの現状調査です。featureB は別の調査エージェントが並行して担当しているため、featureB には立ち入らないでください。
>
> タスク: featureA の現状を調査し、以下を成果物として返してください。
> - featureA に関連するファイルパスの一覧（役割を各 1 行で）
> - 現状の構造（エントリポイント、データの流れ、主要な型・モジュール境界）
> - 制約（既存の依存、外部 API、後方互換の要求、テストの有無など）
> - 未実装・未整備に見える箇所
> - 仕様・要件に関する未解決の疑問（下記エスカレーション参照）
>
> 成果物は「関連ファイルパス・現状の構造・制約の要約」に絞ってください。調査ログの全文やファイルの引用の貼り付けは不要です（結論だけを返してください）。
>
> エスカレーション: design.md から答えが出ない仕様・要件レベルの選択（featureA の想定挙動、対応すべき範囲、featureB との境界の解釈など）に突き当たった場合、**自分で判断しないでください**。疑問・取り得る選択肢・各選択肢のトレードオフ・あなたの推奨を成果物として返してください。判断はオーケストレーターが design.md 経由でユーザーに仰ぎます。実装レベルの技術判断（仕様に影響しない内部設計など）はこの対象外です。迷ったらエスカレーションに倒してください。
>
> 境界: コード・ドキュメント・git のいずれも変更しないこと（`git status` / `git log` / `git show` などの読み取りは可）。featureB の調査、修正提案の実装、リファクタリング、テスト追加はしないこと。タスク範囲外の探索でコンテキストを消費しないこと。
>
> コンテキスト管理: **成果物の末尾に自身のコンテキスト使用率（概算でよい）を必ず記載**してください。compact は行わないこと。使用率が 50% に近づいたら、調査途中でも「そこまでの成果」と「未完了リスト」を明文化して停止してください。続きは新しいエージェントに引き継ぎます。

## 起動順序

1. design.md の存在確認（私が読み取りで実施）。無ければ 委譲 1（ドキュメントエージェント / Opus）を単独で起動
2. design.md のパス確定後、**委譲 2 と委譲 3 を同一ターンで並列起動**（featureA と featureB は独立しており依存関係が無いため）
3. 2 体の成果物を検収。コンテキスト使用率の自己申告が 50% を超えていた場合、そのエージェントは以降続投させず、未完了分があれば新規エージェントに「前任者の成果物」を渡して再開させる
4. 仕様・要件の疑問が返ってきた場合は design.md の「未決事項」に疑問 / 選択肢 / トレードオフ / 推奨を追記し、チャットでは「design.md の未決事項に判断を記入してください」とだけ伝えて停止
5. ユーザーへ報告（エスカレーション項目を先頭に置き、その下に featureA / featureB の現状要約）

## 本プランで起動しないもの

- **実装エージェント / impl.md**: 今回の依頼は調査のみで実装フェーズに入らないため。実装に進む指示が出た時点で、実装エージェント起動の**前に** impl.md を upfront 作成し、その書き込みと同時に別エージェントによるドキュメントレビューをセットで走らせます
- **ドキュメントレビューエージェント**: impl.md への書き込みが発生しないため（発生した全契機で必ず起動する運用は維持）
- **コミットエージェント**: git 書き込み操作が発生しないため。私自身が `git add` / `git commit` 等を直接実行することはありません
