# プラン

この依頼は「バッジを表示する」以外の仕様がほぼ未確定（バッジの定義・付与条件・データソース・表示位置・表示上限・未取得バッジの扱いなど）なので、まず仕様確定を先に置き、実装には入りません。私（オーケストレーター）自身はコード実装・調査・ドキュメント執筆・コードレビュー・git 書き込みを一切行わず、対話と意思決定・委譲・検収に徹します。順序は、(1) `docs/badge-display/design.md` の存在確認（無いので新規作成をドキュメントエージェント／Opus に委譲）と、既存プロフィール画面の構造調査（調査エージェント／Opus）を依存関係が無いので同一ターンで並列起動、(2) 両者の結果をもとに仕様上の疑問を私自身が design.md の「未決事項」に「疑問 / 選択肢 / トレードオフ / 推奨」の形で追記し、チャットには「design.md の未決事項に判断を記入してください」とだけ伝えて停止（選択肢やトレードオフをチャットには一切並べず、確認質問も繰り返しません。ユーザーがチャットで口頭回答した場合も、design.md に転記してから再開します）、(3) ユーザー記入後に design.md を読み直して決定を「決定事項」へ整理、(4) 実装フェーズに入る前に impl.md を upfront 作成（構成・技術的判断・実装ステップ・コミット分割案まで固める。方針が未確定なので Opus）、(5) impl.md への書き込みは必ずドキュメントレビューとセットなので、author とは別のドキュメントレビューエージェント（Opus）を即座に起動、(6) 指摘反映後に実装エージェント（Sonnet、方針は impl.md で固まっているため）へ委譲し、完了時に impl.md の該当セクションを更新させる、(7) その更新分について再度、別のドキュメントレビューエージェント（Opus）を即座に起動、(8) コードレビューエージェント（Opus）で design.md の仕様との乖離・impl.md との整合を確認。全委譲プロンプトに design.md / impl.md のパス・エスカレーション指示・境界・「成果物末尾に自身のコンテキスト使用率を概算で申告し、50% に近づいたら成果と未完了リストを明文化して停止せよ」を含め、申告値が 50% を超えたら続投させず新規サブエージェントへ引き継ぎます（引き継ぎは会話履歴ではなく design.md / impl.md と成果物経由）。コミットについては、このタスクは特定のワークフロースキルの外にあり呼び出し側の規約が無いため、ユーザーの明示指示（`commit して` 等）を待ってからコミットエージェントに委譲します（実装完了を契機にした自発的コミットは行いません）。git の読み取り系（`git status` / `git diff` / `git log`）は意思決定材料として私が直接実行しますが、書き込み系は一切私からは呼びません。最終報告はエスカレーション（design.md 判断待ち項目）を先頭に置いた要約で行います。

前提: ドキュメントの配置は `docs/badge-display/design.md` / `docs/badge-display/impl.md` を想定します（既存の配置規約があればそれに合わせます）。design.md の「未決事項」への追記自体は、エスカレーションプロトコルの規定どおり私が行います（コードやその他ドキュメントの執筆は委譲）。

## エスカレーションの扱い（ステップ 2 の具体）

design.md 作成と調査の結果を受け、私自身が design.md の「未決事項」に以下の論点を「疑問 / 選択肢 / 各選択肢のトレードオフ / 推奨」の形で追記します（想定される論点: バッジの定義と種類、付与条件と付与主体、データソースを新設するか既存概念を再利用するか、プロフィール画面上の表示位置、表示件数の上限と省略時の挙動、未取得バッジを表示するか、他人のプロフィールでの表示可否、バッジ 0 件時の表示）。

追記後、チャットでの私の発話は次の一文だけです。

> design.md の未決事項に <疑問タイトル> を追記しました。判断を記入してください。

選択肢・トレードオフ・推奨をチャットに並べることはせず、「〜という理解で合っていますか？」という確認質問も行いません。ユーザーがチャットで口頭回答した場合は、そのまま進めず design.md に転記してから再開します。記入後は design.md を読み直して決定を検出し、design-impl-docs スキルの「未決事項 → 決定事項の移動」規約に従って整理してから、ステップ 4 に進みます。
