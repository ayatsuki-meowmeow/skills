# プラン

この依頼は「バッジを表示したい」だけで、バッジの種類・獲得条件・データの出どころ・プロフィール画面上の表示形式・獲得ゼロ時の扱いといった**仕様が何も決まっていない**ので、私（オーケストレーター）はまず実装に入らず仕様の空白を埋める側に回ります。私自身がやるのはタスク分解・委譲・成果の検収・エスカレーション・design.md への決定転記の指揮だけで、コード実装・調査・ドキュメント執筆・レビュー・git 書き込みはすべて専門サブエージェントに委譲します。順序は (1) 現状把握のため調査エージェントを 2 体、UI 層とデータ層という独立した観点で同一ターンに並列起動（いずれも読解量が多く中間出力が大きいので委譲対象、モデルは判断が主なので Opus）、(2) その結論をもとにドキュメントエージェント（Opus）で design.md を新規作成し、未決の仕様を「未決事項」節に疑問／選択肢／トレードオフ／推奨の形で書かせる、(3) ここでいったん停止してユーザーへエスカレーションします。バッジ機能は論点が複数（獲得条件の定義・データモデル・表示ルール・既存実績ロジックとの関係）絡み後続の実装・API・UI すべてに影響するため「重い判断」と見なし、AskUserQuestion ではなく **design.md 経由ルート**を選びます。チャットには選択肢やトレードオフを書かず「design.md の未決事項に判断を記入してください」というポインタだけを伝えて止まります（チャットで自由記述の Q&A を重ねることはしません。ユーザーが口頭で答えてきた場合も、必ず design.md の「決定事項」に転記してから再開します）。(4) 決定が入ったらドキュメントエージェント（Sonnet）に決定事項の転記と **impl.md の初版作成**を委譲します。impl.md は実装フェーズに入る前に必ず存在させ、その書き込みに対しては**書いたエージェントとは別の**ドキュメントレビューエージェント（Opus、reviewer != author）を起動して design.md との整合を確認します。(5) その後に実装エージェント（Sonnet、方針が impl.md まで落ちているため）へ委譲し、完了後にコードレビューエージェント（Opus）で design.md の仕様との乖離と impl.md との整合を見ます。(6) git 書き込みは規模を問わず私が直接叩かず、ユーザーの明示指示（「コミットして」等）を待ってからコミットエージェントに委譲します（実装が終わったからついでにコミットはしません。`git status` / `git diff` などの読み取りだけは判断材料として私が直接実行します）。ユーザーへの報告では、未決事項＝エスカレーションを必ず先頭に置きます。

## 委譲プロンプト（役割 / モデル）

### 1. 調査エージェント — プロフィール画面 UI 層（model: opus、2 と同一ターンで並列起動）

> あなたはコードベース調査の専門エージェントです。コードは一切変更しないでください。
>
> **コンテキスト**: 本タスクのドキュメントは `docs/user-badges/design.md`（未作成）・`docs/user-badges/impl.md`（未作成）に置く予定です。まだ存在しないため、この調査結果が design.md の初版の材料になります。ユーザーの依頼は「ユーザープロフィール画面にバッジを表示する機能を追加したい」で、仕様は未確定です。
>
> **タスク**: プロフィール画面のフロントエンド側の現状を調べ、次を成果物として返してください。
> 1. プロフィール画面を構成するファイルのパス一覧（ページ / コンポーネント / スタイル / ルーティング定義）
> 2. 画面がユーザー情報を受け取っている経路（props / データ取得フック / API クライアント）とその型定義のパス
> 3. 既に「アイコンの並び」「タグ」「実績表示」のような、バッジ表示に流用できそうな既存 UI パターンがあるか
> 4. 表示要素を 1 つ増やすときに触る必要があるファイルの範囲と、レイアウト上の制約
>
> 出力は関連ファイルパス・現状の構造・制約の要約に絞ってください。調査ログや読んだファイルの中身の転記は不要です。
>
> **エスカレーション**: 仕様・要件に関する疑問（どのバッジをどこに何個出すのか、獲得ゼロ時の表示など）は**あなたが判断しないでください**。疑問と考えられる選択肢を成果物の末尾に列挙して返し、決定はオーケストレーター経由でユーザーに仰ぎます。
>
> **境界**: コードを変更しない。ドキュメントを作成・更新しない。git 操作をしない。設計案や実装案の提示は不要で、現状の事実と制約のみ返す。

### 2. 調査エージェント — データ層 / 既存実績ロジック（model: opus、1 と同一ターンで並列起動）

> あなたはコードベース調査の専門エージェントです。コードは一切変更しないでください。
>
> **コンテキスト**: 本タスクのドキュメントは `docs/user-badges/design.md`（未作成）・`docs/user-badges/impl.md`（未作成）に置く予定です。ユーザーの依頼は「ユーザープロフィール画面にバッジを表示する機能を追加したい」で、バッジの定義・獲得条件は未確定です。
>
> **タスク**: バッジの供給源になり得るサーバー / データ層の現状を調べ、次を成果物として返してください。
> 1. ユーザーモデルとその周辺スキーマ（マイグレーション / スキーマ定義のパス）
> 2. 「実績」「称号」「レベル」「達成」等、バッジ相当の概念が既に存在するか。あるなら定義とその算出ロジックのパス、無いならその旨
> 3. プロフィール画面向けのユーザー情報を返している API / エンドポイント / クエリのパスと、レスポンスの形
> 4. バッジ相当データを追加するとしたら、既存構造のどこに接続するのが自然か（事実として存在する拡張ポイントのみ。設計提案は不要）
>
> 出力は関連ファイルパス・現状の構造・制約の要約に絞ってください。
>
> **エスカレーション**: バッジの獲得条件・付与タイミング・データの持ち方といった仕様レベルの疑問は**あなたが決めないでください**。疑問と選択肢を列挙して返してください。
>
> **境界**: コードを変更しない。マイグレーションを作らない。ドキュメントを作成・更新しない。git 操作をしない。

### 3. ドキュメントエージェント — design.md 新規作成（model: opus、1・2 の成果物受領後）

> あなたはドキュメント作成の専門エージェントです。コードは一切変更しないでください。ドキュメント運用は design-impl-docs スキルの規約に従ってください。
>
> **コンテキスト**: `docs/user-badges/design.md` を新規作成します（未作成）。impl.md はこの段階では作成しません。ユーザーの依頼は「ユーザープロフィール画面にバッジを表示する機能を追加したい」。前段の調査エージェント 2 体の成果物を下記に貼ります。
> - UI 層調査の結果: <調査エージェント 1 の成果物を全文貼付>
> - データ層調査の結果: <調査エージェント 2 の成果物を全文貼付>
>
> **タスク**: design.md の初版を作成してください。
> 1. 「背景 / 目的」: ユーザーの依頼をそのまま要約する（勝手に目的を拡張しない）
> 2. 「現状」: 調査結果から確定している事実と制約のみを書く
> 3. 「未決事項」: 仕様が決まっていない論点を列挙し、各論点について **疑問 / 選択肢 / トレードオフ / 推奨** の 4 点を書く。少なくとも次を含めること — バッジの種類と獲得条件の定義元、バッジデータの持ち方（既存概念への相乗り vs 新規テーブル）、プロフィール画面での表示位置・件数・並び順、未獲得／獲得ゼロ時の表示、他ユーザーのプロフィールでも見えるのかという公開範囲
> 4. 「決定事項」節は見出しだけ作り、空にしておく（ユーザーが未決事項に判断を記入した後、転記して埋める運用）
>
> **エスカレーション**: 未決事項をあなたの推測で決定事項に書き込むことは禁止です。判断が必要なものはすべて「未決事項」に残してください。「推奨」を書くのは構いませんが、それは推奨であって決定ではないと明示してください。
>
> **境界**: コードを変更しない。impl.md を作らない。git 操作をしない。選択肢やトレードオフの本文はチャット向けに要約せず design.md 内に書ききる（チャットにはポインタしか出しません）。

**→ ここで停止し、ユーザーに「`docs/user-badges/design.md` の「未決事項」に判断を記入してください」とだけ伝える。** 選択肢・トレードオフ・推奨はチャットに再掲しない（design.md にあるため二重管理になる）。判断が入るまで実装フェーズには進まない。

### 4. ドキュメントエージェント — 決定事項の転記と impl.md 初版作成（model: sonnet、ユーザー判断後）

> あなたはドキュメント作成の専門エージェントです。コードは一切変更しないでください。ドキュメント運用は design-impl-docs スキルの規約に従ってください。
>
> **コンテキスト**: `docs/user-badges/design.md`（作成済み・ユーザーが未決事項に判断を記入済み）、`docs/user-badges/impl.md`（未作成）。両方の状況を把握するため design.md を先に全文読んでください。
>
> **タスク**:
> 1. design.md の「未決事項」に記入されたユーザーの判断を、design-impl-docs スキルの「未決事項 → 決定事項の移動」節の手順に従って「決定事項」へ転記する。判断されていない項目は未決事項に残す
> 2. 転記後の決定事項をもとに `docs/user-badges/impl.md` の初版を作成する。記載範囲は design-impl-docs スキルの「配置」節に従う。「構成」「実装状況」「技術的判断」を、現時点で確定している範囲で書く（実装は未着手なので実装状況はすべて未着手として明示する）
> 3. impl.md は「コードを読めばわかること」の書き写しにも、実装の現在地が読めない抽象論にもしないこと
>
> **エスカレーション**: 決定事項に転記できるのはユーザーが明示的に判断した内容だけです。曖昧なまま埋めず、判断が読み取れない項目は未決事項に残して、その旨を成果物で報告してください。
>
> **境界**: コードを変更しない。design.md の決定内容を書き換えない（転記のみ）。git 操作をしない。実装作業をしない。

### 5. ドキュメントレビューエージェント — design.md / impl.md の整合（model: opus、4 とは別エージェント）

> あなたは design.md と impl.md の整合をレビューする専門エージェントです。コードもコミットも触りません。impl.md を書いたエージェントとは別のあなたが見ることで reviewer != author を担保しています。
>
> **コンテキスト**: `docs/user-badges/design.md`、`docs/user-badges/impl.md`。両方を読んでください。impl.md は初版が作成されたばかりで、実装は未着手です。
>
> **タスク**: 次の観点でレビューし、指摘のリストを返してください。
> - design.md の決定事項が impl.md の「実装状況」に反映されているか（決定済みなのに未着手扱いになっている項目が無いか）
> - impl.md の「技術的判断」が design.md の仕様・制約と矛盾していないか
> - design.md の未決事項に該当する内容を impl.md 側で勝手に「実装済み」扱いしていないか
> - design.md の変更履歴と impl.md の記述が同期しているか（旧仕様の記述が残っていないか）
> - impl.md の記述が具体的すぎて「コードを読めばわかること」の書き写しになっていないか、逆に抽象的すぎて実装の現在地が読み取れないか
>
> 成果物は指摘のリストで、各指摘に `category_hint`（仕様乖離 / 記述漏れ / 記述過剰 / 未決先取り / 履歴不整合 のいずれか）と該当箇所のパス・要約を付けてください。
>
> **エスカレーション**: 仕様そのものへの疑問（design.md の決定が不足している等）は、あなたが埋めずに指摘として返してください。ユーザーへのエスカレーションはオーケストレーターが行います。
>
> **境界**: ドキュメントを書き換えない（指摘のみ）。コードを触らない。git 操作をしない。

### 6. 実装エージェント（model: sonnet、5 の指摘対応後）

> あなたは実装の専門エージェントです。
>
> **コンテキスト**: `docs/user-badges/design.md`（仕様・要件、決定事項が記入済み）と `docs/user-badges/impl.md`（構成・実装状況・技術的判断）を**まず両方読んでから**着手してください。関連ファイルのパスは impl.md の「構成」節にあります。
>
> **タスク**: design.md の「決定事項」に厳密に従って、ユーザープロフィール画面のバッジ表示機能を実装してください。完了時に impl.md の「構成」「実装状況」「技術的判断」の該当セクションを更新すること。成果物は「変更ファイル一覧と変更概要、未解決の疑問」です。
>
> **エスカレーション**: design.md から答えが出ない仕様・要件の選択に突き当たったら、**自分で決めずに**そこで手を止め、疑問と選択肢を成果物として返してください。決定はユーザーが行います。仕様に影響しない内部設計（コンポーネント分割の粒度・ライブラリの使い方など）はあなたが判断し、理由を impl.md の「技術的判断」に記録してください。
>
> **境界**: design.md の決定事項の範囲外の変更をしない（リファクタリング・最適化・無関係なテスト追加・整形を含む）。git 操作は一切しない（`git add` / `git commit` も禁止。コミットは別のコミットエージェントが行います）。design.md を書き換えない。

>
> **タスク**: 実装差分をレビューし、指摘のリスト（該当ファイル:行・重大度・理由）を返してください。観点には必ず次を含めること。
> - design.md の仕様との乖離（決定事項どおりに実装されているか、未決事項を勝手に実装していないか）
> - impl.md の「実装状況」「技術的判断」との整合（記述と実物がずれていないか）
>
> **エスカレーション**: 仕様の解釈が割れる箇所は、あなたが正解を決めずに疑問として返してください。
>
> **境界**: コードを修正しない（指摘のみ）。ドキュメントを書き換えない。git 操作をしない。

### 8. コミットエージェント（model: sonnet、**ユーザーが明示的にコミットを指示した場合のみ**起動）

> あなたは未コミット変更を staging → commit する専門エージェントです。プロジェクトにコミット規約スキル（例: commit-workflow）があればそれに従ってください。
>
> **コンテキスト**: ユーザープロフィール画面のバッジ表示機能の実装差分が未コミットの状態です。仕様は `docs/user-badges/design.md`、実装詳細は `docs/user-badges/impl.md` にあります。ユーザーからコミットの明示指示が出ています。
>
> **タスク**: 未コミット差分を意味単位に分割して commit してください。分割単位・メッセージ文言はあなたが決めてください。成果物は「作成したコミットのハッシュ・分割の内訳・残った未コミット差分の有無」です。
>
> **エスカレーション**: 分割単位やメッセージ文言に迷ったら自己判断で強行せず、疑問として返してください（オーケストレーター経由でユーザーに確認します）。履歴書き換え（`rebase` / `push --force` / `reset --hard`）は今回のタスク範囲外なので、必要だと感じたら実行せず報告してください。
>
> **境界**: コード修正・ファイル追加・整形など範囲外の変更を一切加えない。push しない。

## 補足: 判断の根拠

- **エスカレーションのルート選択**: バッジ機能は論点が複数絡み（獲得条件の定義・データモデル・表示ルール・公開範囲）、決定が後続の実装／API／UI 複数タスクに影響し、後から根拠を追いたい種類の判断なので「重い」と分類し design.md ルートを選択。選択肢が 2〜4 個でトレードオフが 1 行で書ける軽い判断なら AskUserQuestion（1 往復上限）を使いますが、今回は該当しません。
- **不変条件**: ルートを問わず、ユーザーの決定は design.md の「決定事項」に転記してから作業を再開します。転記前に実装フェーズへ進みません。ユーザーがチャットで口頭回答した場合も同じで、口頭合意のまま進めません。
- **委譲しないもの**: 調査結果の受領後に判明した「既知パスの単発参照」レベルの確認は私が直接読みます。また、design.md の決定に沿った 1 ファイル数行の追従修正で lint / typecheck で検証が閉じるものは私が直接編集します（複数ファイルに波及する・仕様解釈が必要になった時点で実装エージェントへ委譲）。
- **git**: 書き込み系は例外なくコミットエージェントに委譲。読み取り系（`git status` / `git diff` / `git log`）は判断材料として私が直接実行します。
- **コンテキスト管理**: サブエージェントは 1 体 1 役目で使い切り、役目が終わったら新規に委譲します（compact はさせません）。引き継ぎは会話履歴のコピーではなく design.md / impl.md と成果物経由で行います。コンテキスト使用率の自己申告は求めません（観測できない推測値なので閾値判定に使いません）。
- **報告**: 各段の検収後、ユーザーへの報告は「エスカレーション（未決事項・要判断項目）」を先頭に置き、その後に成果の要約を書きます。
