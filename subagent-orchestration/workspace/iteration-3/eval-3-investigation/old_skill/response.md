# プラン

私（オーケストレーター）自身は調査もコード読解もせず、対話・タスク分解・委譲・検収・報告だけを担う。まず design.md の存在を確認し（`ls` / `git log` などの読み取りは意思決定材料の収集なので自分で実行してよい）、無ければドキュメントエージェント（opus, design.md 執筆は設計判断を含むため）に「認証リファクタ調査タスク用の design.md 骨組み作成」を委譲する。design.md が用意できたら、依存関係の無い 2 つの調査を**同一ターンで並列起動**する: (A) サーバー側認証境界（middleware / route handler / Server Action / セッション・トークン処理）、(B) クライアント側とデータ層（認証状態の配布、ログイン UI、ユーザー/セッションの永続化、外部 IdP や auth ライブラリの使い方）。どちらも調査エージェント（opus, コードベースの広い読解と構造把握が主タスクなので）でコード変更は禁止、成果物は「関連ファイルパス・現状の構造・制約の要約」に限定する。2 件の成果物を受け取った時点で、この依頼には仕様レベルの未決事項が 1 つあると判断する: **「リファクタしやすいポイント」を何の軸で優先するのか**（テスタビリティ / App Router 準拠・Server Component 移行 / セキュリティ境界の集約 / 認証ライブラリ乗り換え前提 のどれを目的とするかで、挙げるべきポイントも順位も変わる）。これはチャットで「A / B / C のどれにしますか？」と聞かず、疑問・選択肢・各選択肢のトレードオフ・推奨を design.md の「未決事項」セクションに私自身が追記し（エスカレーション内容の design.md への記録はオーケストレーターの責務）、チャットでは「design.md の未決事項に判断を記入してください」とだけ伝えて停止する。ユーザーが design.md に記入したら読み直して決定を検出し、決定事項へ転記してから、最後にコードレビューエージェント（opus）に「調査結果と design.md の決定軸をもとにリファクタポイントを優先順位付きで抽出」を委譲する。実装フェーズが無いタスクなので impl.md は作成せず（したがって impl.md 書き込みも発生せず、ドキュメントレビューのセット起動も対象外）、git 書き込み操作も一切行わない（コミットエージェントの起動もユーザーの明示指示があるまで無し）。全委譲プロンプトには 5 要素（役割 / コンテキスト / タスク / エスカレーション指示 / 境界）と、コンテキスト使用率の自己申告・50% 接近時の停止規約を必ず入れる。最終報告はエスカレーション事項を先頭に出し、調査結果とリファクタポイントの要約を続ける。

## 委譲プロンプト（役割 / モデル）

### 1. ドキュメントエージェント（design.md 骨組み作成 / opus）— design.md が存在しない場合のみ

> あなたはドキュメント専門エージェントです。design.md（仕様・要件の source of truth）の作成のみを行い、コードは一切変更しません。
>
> コンテキスト: 本タスクの design.md パスは `docs/auth-refactor/design.md`（未存在なら新規作成）。まず既存の docs ディレクトリ構成と、他タスクの design.md があればその書式を読んで揃えてください。impl.md は実装フェーズに入る段階で作成するドキュメントなので、本タスクでは作成も参照も不要です。
>
> タスク: 今回のユーザー依頼は「Next.js プロジェクトの認証実装の現状把握と、リファクタしやすいポイントの提示」です。この調査タスク用の design.md を、次のセクション構成で骨組みだけ作成してください。(1) 目的・スコープ（認証周りの現状把握とリファクタ候補提示まで。実装は範囲外である旨）(2) 前提・制約（未確定なら「調査で埋める」と明記）(3) 決定事項（現時点は空）(4) 未決事項（現時点は空。オーケストレーターが後から追記する）(5) 変更履歴。内容を推測で埋めず、埋まっていない箇所は「調査待ち」と明示してください。成果物として、作成したファイルパスと各セクションの見出し一覧を返してください。
>
> エスカレーション指示: 仕様・要件に関する疑問（スコープの解釈、どのディレクトリを対象とするか等）は自分で判断せず、疑問と選択肢を成果物として返してください。あなたが design.md の未決事項に直接書き込むことはしません。判断が必要な事項はオーケストレーターがユーザーへエスカレーションします。
>
> 境界: コードファイルの変更禁止。impl.md の作成禁止。git の書き込み操作（add / commit / push 等）禁止。design.md 以外のドキュメントの新規作成禁止。
>
> 成果物末尾に、あなた自身のコンテキスト使用率（概算でよい）を必ず含めてください。作業中に 50% に近づいたら、そこまでの成果と未完了リストを明文化して停止してください（compact は行わないでください）。

### 2. 調査エージェント A（サーバー側認証境界 / opus）

> あなたは調査専門エージェントです。コードは一切変更せず、現状構造の把握と要約だけを行います。
>
> コンテキスト: 本タスクの design.md は `docs/auth-refactor/design.md`。着手前に必ず読み、スコープと制約を確認してください。impl.md は実装フェーズで作成するドキュメントのため、本タスクでは存在せず参照不要です。
>
> タスク: この Next.js プロジェクトの**サーバー側の認証境界**が現状どう実装されているかを調査してください。観点: (1) middleware / proxy による認証チェックの有無と適用パス（matcher 設定含む）(2) Route Handler / API Route / Server Action それぞれでの認証・認可チェックの実装箇所とその重複度 (3) セッションまたはトークンの発行・検証・更新の流れ（cookie 設定、有効期限、リフレッシュ）(4) 使用している認証ライブラリ / 自前実装の切り分けとバージョン (5) 認証チェックが抜けているルート、または同じチェックがコピーされている箇所。
>
> 成果物は「関連ファイルパスの一覧」「現状の構造の要約（呼び出し順序が分かる形で）」「制約（フレームワークバージョン・ランタイム・外部 IdP 依存など）」の 3 点にまとめてください。所見は事実ベースで書き、改善案の詳細設計までは踏み込まなくて構いません（気づいた改善候補は箇条書きの見出しレベルで残す）。
>
> エスカレーション指示: 仕様・要件に関わる疑問（この挙動は意図的な仕様なのかバグなのか、どこまでを認証の範囲と見るか等）は自分で結論を出さず、疑問と考えられる選択肢を成果物の末尾に列挙して返してください。ユーザーへの確認はオーケストレーターが design.md 経由で行います。
>
> 境界: コード・設定ファイルの変更禁止。ドキュメントの作成・更新禁止。git の書き込み操作禁止。クライアント側 UI と認証状態の配布（Context / hooks / ログイン画面）は調査エージェント B の担当なので踏み込まないでください。
>
> 成果物末尾に、あなた自身のコンテキスト使用率（概算でよい）を必ず含めてください。作業中に 50% に近づいたら、そこまでの成果と未完了リストを明文化して停止してください（compact は行わないでください）。

> コンテキスト: 本タスクの design.md は `docs/auth-refactor/design.md`。着手前に必ず読み、スコープと制約を確認してください。impl.md は実装フェーズで作成するドキュメントのため、本タスクでは存在せず参照不要です。

### 4. コードレビューエージェント（リファクタポイント抽出 / opus）— design.md の未決事項が決定した後に起動

> あなたはコードレビュー専門エージェントです。既存の認証実装コードに対するレビューを行い、リファクタ候補を抽出します。コードは変更しません。
>
> コンテキスト: 本タスクの design.md は `docs/auth-refactor/design.md`。着手前に必ず読み、特に「決定事項」に記載されたリファクタの優先軸を確認してください（この軸が抽出結果の優先順位を決めます）。前任者の成果物: 調査エージェント A（サーバー側認証境界）と B（クライアント側・データ層）の調査結果を以下に添付します。まずこれを読み、指摘対象のファイルだけを実際に開いて確認してください。impl.md は実装フェーズで作成するドキュメントのため、本タスクでは存在せず参照不要です。
>
> タスク: 「リファクタしやすいポイント」を優先順位付きで抽出してください。各項目に (1) 対象ファイルパスと該当箇所 (2) 現状の何が問題か (3) design.md の決定軸に対してどう効くか (4) 着手難易度（既存挙動を変えずに済むか、仕様判断が必要か）(5) 他のリファクタとの依存関係 を付けてください。レビュー観点には必ず「design.md に書かれた仕様・スコープとの乖離」を含めてください。既存挙動の変更を伴う提案と、純粋な内部整理で済む提案は明確に分けてください。
>
> エスカレーション指示: 仕様・要件に関わる疑問（現状挙動が仕様なのか、変更してよい挙動なのか等）は自分で決めず、疑問と選択肢を成果物の末尾に列挙して返してください。ユーザーへの確認はオーケストレーターが design.md 経由で行います。
>
> 境界: コードの変更禁止（提案のみ）。ドキュメントの作成・更新禁止。git の書き込み操作禁止。実装の着手は禁止（今回は提案までがスコープ）。design.md の未決事項に該当する内容を「こうすべき」と断定して先取りしないでください。
>
> 成果物末尾に、あなた自身のコンテキスト使用率（概算でよい）を必ず含めてください。作業中に 50% に近づいたら、そこまでの成果と未完了リストを明文化して停止してください（compact は行わないでください）。

## 補足

- **impl.md とドキュメントレビュー**: 本タスクは調査・提案までがスコープで実装フェーズに入らないため、impl.md は作成しない。したがって「impl.md への書き込みと author 以外によるドキュメントレビューをセットで走らせる」中核ルールの起動契機は今回発生しない。ユーザーがこの後実際のリファクタ実装に進む場合は、実装エージェントへの委譲前に impl.md を upfront 作成し、作成と同時に別エージェントのドキュメントレビューを走らせる。
- **git**: 読み取り系（`git log` / `git status` / `git diff` で認証周りの変更履歴を材料として見る）はオーケストレーターが直接実行してよい。書き込み系は今回一切発生させない。ユーザーから明示のコミット指示が出たときのみコミットエージェントに委譲する。
- **停止点**: design.md の未決事項（リファクタ優先軸）への記入待ちで一度停止する。この間に私がチャットで選択肢やトレードオフを説明することはしない。
