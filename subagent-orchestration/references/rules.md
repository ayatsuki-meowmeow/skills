# サブエージェントオーケストレーション — ルール本体

## なぜこの体制か

メインエージェント（オーケストレーター）のコンテキストを、ユーザーとの対話と意思決定に集中させるため。調査ログやコード編集の詳細でメインのコンテキストを消費すると、対話の品質と判断の精度が落ちる。作業の詳細はサブエージェントが抱え、メインは**結論だけ**を受け取る。

もう 1 つの目的は決定権の明確化。仕様・要件を決めるのは常にユーザーであり、サブエージェントにもオーケストレーター自身にも「たぶんこうだろう」で仕様を決めさせない。

## 役割分担

**オーケストレーター（このエージェント）がやること:**

- ユーザーとの対話、要求の明確化
- タスクの分解、サブエージェントへの委譲、進行管理
- 仕様・要件に関する疑問のエスカレーションと、決定の design.md への記録
- サブエージェントの成果の検収、ユーザーへの報告
- 「委譲の判断基準」で委譲対象外と判断した軽微な修正の直接実行
- サブエージェントの役目の切り分けと、役目が終わったときの新規エージェントへの引き継ぎ（詳細は「サブエージェントのコンテキスト管理」参照）

**オーケストレーターがやらないこと:** コード実装・調査・ドキュメント執筆・コードレビューは、原則として対応する専門サブエージェント（実装 / 調査 / ドキュメント / レビュー / コミット）に委譲する。何を委譲するかは下記「委譲の判断基準」で決める。

### 委譲の判断基準

委譲はメインのコンテキストを対話と意思決定に集中させるための**手段**であって、それ自体が目的ではない。1 体起動するたびに委譲プロンプトの作成と成果物の受領という往復コストが乗る。基準なしに「とにかく委譲」すると、3 行の修正に実装エージェント → lint → ドキュメントレビュー → 5 レンズ + 採点 → コミットエージェントが起動する。

**委譲する:**

- 真に独立していて並列化できる作業（複数ファイル・複数モジュールにまたがる調査、独立した機能単位の実装）
- 中間出力が大量に出る作業（調査ログ、広範囲の差分読解）。メインには結論だけを返させたいもの
- reviewer != author を担保する必要がある作業（コードレビュー・ドキュメントレビュー）
- **git 書き込み操作。これは効率ではなく権限境界の問題なので、規模を問わず例外なくコミットエージェントに委譲する**（下記「git 操作の扱い」）

**委譲しない:**

- 単一ファイル・数行に収まり、仕様判断を伴わず、lint / typecheck で検証が閉じる修正。オーケストレーターが直接編集してよい。この境界を超えたら（複数ファイルに波及する / 仕様の解釈が必要 / 検証手段が目視しかない）実装エージェントに委譲する
- 数回のツール呼び出しで完結する読み取り（既知パスの参照、単発の grep）
- 自分の作業の検証・ダブルチェックを目的とした起動
- 委譲プロンプトを書くコストが作業そのものを上回る作業

**起動数:** 1 体で足りるなら 1 体にする。同じ対象を同じ観点で見せる多重起動はしない（観点が実際に独立している場合に限り複数起動する）。

判断に迷ったら、その作業でメインのコンテキストに流れ込む中間出力の量を見る。多いなら委譲、少ないなら直接やる。

### git 操作の扱い

- **書き込み系（`git add` / `git commit` / `git rebase` / `git reset` / `git push` など HEAD やリモート・履歴を動かす操作）はすべてコミットエージェントに委譲する**。オーケストレーター自身は Bash からこれらを直接呼ばない。コマンド文字列・分割単位・メッセージ文言はコミットエージェントに決めさせる（迷ったらユーザーへエスカレーション）。
- 読み取り系（`git status` / `git diff` / `git log` / `git show` など）は例外。意思決定の材料を集めるのはオーケストレーターの責務なので、直接実行してよい。
- **コミットのタイミングは呼び出し側ワークフローの規約に従う**。例: implement-review-loop はループ収束を契機にコミットエージェントを起動する。呼び出し側スキルに規約が無い場合や、ワークフロー外での書き込み操作は、ユーザーの明示指示（`commit して` 等）を待ってから委譲する。「実装が終わったのでついでにコミット」のような、規約にもユーザー指示にも根拠のない自発的コミットは禁止。
- 履歴書き換え・共有ブランチ操作（`git rebase` / `git push --force` / `git reset --hard` など）は特にユーザー確認必須。オーケストレーターがユーザーと相談したうえで、実行自体はコミットエージェントに委譲する。

## ドキュメント連携

ドキュメント運用は **design-impl-docs スキル**の規約に従う（design.md = 仕様・要件、impl.md = 実装詳細、レビューはいずれもユーザー）。オーケストレーターの責務:

- タスク開始時に **design.md の存在を確認し、無ければ作成する**。**実装フェーズに入る前に impl.md も必ず作成する**（作成自体はドキュメントエージェントに委譲してよい）。両ドキュメントの作成タイミング・記載範囲は design-impl-docs スキルの「配置」節に従う
- **`impl.md` への書き込みはドキュメントレビューとセットで実施する。** 起動契機・skip 条件・指摘への対応方針は design-impl-docs スキルの「中核ルール」節に従う（実体はそちら。ここに再掲しない）。レビュー実行は下記「ドキュメントレビューエージェント」役に委譲する
- 委譲プロンプトに必ず該当タスクの design.md と impl.md のパスを含める。実装エージェントには「impl.md の該当セクションを更新すること」「範囲外の変更をしないこと」を明示する

## 委譲の仕方

役割は委譲時のプロンプトで定義する。すべての委譲プロンプトに含める共通要素:

1. **役割** — 何の専門エージェントとして振る舞うか
2. **コンテキスト** — design.md / impl.md のパスと「まず読め」の指示
3. **タスク** — 何をして何を成果物として返すか
4. **エスカレーション指示** — 下記プロトコル参照
5. **境界** — やらないこと（タスク範囲外の変更をしない、など）

### 役割別の差分

- **調査エージェント**: 成果物は「関連ファイルパス・現状の構造・制約の要約」。コードは変更しない。
- **実装エージェント**: design.md の仕様に厳密に従い、完了時に impl.md の構成・実装状況を更新する。成果物は「変更ファイル一覧と変更概要、未解決の疑問」。コミットはしない。
- **ドキュメントエージェント**: design.md / impl.md の更新のみで、コードは変更しない。
- **コードレビューエージェント**: 実装差分（コード）に対するレビュー。「design.md の仕様との乖離」「impl.md の実装状況との整合」を必ず観点に含める。詳細は code-review-agent skill に従う。
- **ドキュメントレビューエージェント**: **design.md と impl.md の整合をレビューする専門エージェント**。コードもコミットも触らない。`impl.md` を書いたエージェントとは別のエージェントで起動する（reviewer != author。起動契機は design-impl-docs スキルの「中核ルール」節）。観点:
  - design.md の決定事項が impl.md の「実装状況」に反映されているか（決定済みなのに未着手扱いになっている項目が無いか）
  - impl.md の「技術的判断」が design.md の仕様・制約と矛盾していないか
  - design.md の未決事項に該当する内容を impl.md 側で勝手に「実装済み」扱いしていないか
  - design.md の変更履歴と impl.md の記述が同期しているか（旧仕様の記述が impl.md に残っていないか）
  - impl.md の記述が具体的すぎて「コードを読めばわかること」の書き写しになっていないか、逆に抽象的すぎて実装の現在地が読み取れなくなっていないか

  成果物は「指摘のリスト（各指摘に category_hint: 仕様乖離 / 記述漏れ / 記述過剰 / 未決先取り / 履歴不整合 のいずれか）＋ 該当箇所のパス＋要約」。分類 → 記録は呼び元（implement-review-loop）の指摘分類ステップに合流させる。
- **コミットエージェント**: 未コミット変更を staging → commit する専門エージェント。プロジェクトにコミット規約スキル（例: commit-workflow）があればそれに従う。分割単位・メッセージ文言に迷ったらユーザーへエスカレーション（自己判断で強行しない）。範囲外の変更（コード修正・ファイル追加・整形）は一切加えない。成果物は「作成したコミットのハッシュ・分割の内訳・残った未コミット差分の有無」。

### 並列実行

依存関係のないタスクは、同一ターンで複数のサブエージェントを起動して並列化する（例: 独立した 2 モジュールの調査、実装と並行したドキュメント更新）。依存があるタスクは前段の成果物を受け取ってから次を委譲する。

並列化の対象になるのは「委譲の判断基準」で委譲すると判断した作業のみ。並列にできるからといって、直接やれば済む作業を分割して起動しない。

## エスカレーションプロトコル

仕様・要件に関わる疑問（design.md から答えが出ない選択）が発生したときは、**発生源を問わず**（サブエージェントが surface した / オーケストレーター自身が気づいた / タスク着手時の仕様確認 のいずれも）このプロトコルに乗せる。サブエージェントは自分で判断せず、疑問と選択肢を成果物として返す（委譲プロンプトで必ず指示しておく）。

### 不変条件

ルートに関わらず、**ユーザーの決定は Claude が design.md の「決定事項」に転記してから作業を再開する**（転記の手順は design-impl-docs スキルの「未決事項 → 決定事項の移動」節）。転記前に実装を進めない。この不変条件を満たすことで:

- 決定と根拠が単一の source of truth に集まり、後から追える
- 後続のサブエージェントが design.md を読むだけで決定に到達できる

**ここは緩めない。** 以下のルート選択は「どこで質問するか」の話であって、「どこに決定を残すか」の話ではない。

### ルートの選択

| 判断の重さ | ルート |
|---|---|
| **軽い** — 選択肢が 2〜4 個で、各選択肢のトレードオフが 1 行で書ける | **AskUserQuestion** で選択肢を提示し、1 クリックで回答をもらう |
| **重い** — 複数の論点が絡む / 後から根拠を追いたい / 決定が後続の複数タスクに影響する | **design.md 経由**。「未決事項」に「疑問 / 選択肢 / トレードオフ / 推奨」を書き、チャットでは「design.md の <該当セクション> に判断を記入してください」とだけ伝えて停止する |

**AskUserQuestion は 1 往復が上限。** 1 回で閉じない場合（回答が新たな論点を生んだ / 選択肢が想定と噛み合わなかった）は、そこで design.md ルートに切り替える。チャットで Q&A を重ねない — 往復が続くとチャットに判断の経緯が散り、後続のサブエージェントが到達できない状態に戻る。

**design.md ルートでは、選択肢・トレードオフ・推奨をチャットに書かない。** design.md 側に書いてあるので二重管理になる。チャットはポインタ交換にとどめる。

**ユーザーがチャットで口頭回答した場合、必ず design.md に転記してから進める。** ユーザー側から自発的にチャットで答えが返ってくることはある（AskUserQuestion を使わなかった場合も含む）。その場合もオーケストレーターが転記を担い、口頭合意のまま作業を進めない。

技術的な実装判断（仕様に影響しない内部設計・ライブラリの使い方など）はエスカレーション不要。サブエージェントが判断し、impl.md に理由を記録する。迷ったらエスカレーションに倒す。

## サブエージェントのモデル選択

タスク性質に応じて Agent ツールの `model` パラメータでモデルを切り替える。省略時は親（オーケストレーター）を継承する。

**マッピング:**

- **Opus**（`model: "opus"`）: 調査・レビュー・設計・design.md 執筆。コードベースの広い読解、仕様との乖離検出、アーキテクチャ判断など、思考と判断が主のタスク。
- **Sonnet**（`model: "sonnet"`）: 実装・impl.md 更新など定型ドキュメント作業。design.md / impl.md で仕様と方針が固まっており、思考の余地が小さいタスク。

**判断基準:** impl.md に落とせるレベルまで方針が決まっているか。決まっていれば Sonnet、決まっていない・判断を委ねる余地があるなら Opus。迷ったら Opus に倒す（後で下げる方が安全）。

オーケストレーター自身のモデルは変えない（対話・意思決定は思考重視）。

## サブエージェントのコンテキスト管理

サブエージェントは 1 体に役目を継ぎ足していくほど出力品質が落ちる。役目単位で使い切り、次は新規に委譲する。

**ルール:**

- **compact 禁止**: サブエージェントの中で compact（要約による圧縮）は行わせない。compact が必要な状態になった時点で、そのサブエージェントは役目を終える。続きは新規サブエージェントに引き継ぐ。
- **役目単位で使い切る**: 1 体のサブエージェントには 1 つの役目を渡し、終わったら次は新規に委譲する。「まだ動くから」で別の役目を継ぎ足さない。継ぎ足すと指示忘れ・仕様逸脱・冗長な出力の原因になる。
- **ウィンドウの小さいモデルは早めに区切る**: Sonnet / Haiku サブエージェントは Opus よりウィンドウが小さいので、広範囲・長時間のタスクでは途中で成果と未完了リストを明文化させて引き継ぐ。

**自己申告に依存しない:** かつては「成果物末尾にコンテキスト使用率を自己申告させ、50% で切り替える」という規約だったが撤廃した。モデルは自分のコンテキスト使用率を観測できないので返ってくるのは推測値であり、それを閾値判定の入力にしても意味を成さない。切り替えは**役目の区切り**で判断する。

**引き継ぎ方:**

引き継ぎは会話履歴のコピーではなく、design.md / impl.md と成果物（コード・調査結果）経由で行う。オーケストレーターが以下をやる:

1. 現サブエージェントに **最終成果物と未解決事項を明文化して返させる**（暗黙知を残さない）
2. 必要なら成果物・決定事項を design.md / impl.md に反映（委譲してよい）
3. 新規サブエージェントに、通常の委譲プロンプト（役割・コンテキスト・タスク・エスカレーション指示・境界）＋「前任者の成果物: <path>」を渡して再開する

サブエージェント側のコンテキストではなく、**ドキュメントと成果物**が真実の source。これがオーケストレーション体制のそもそもの前提と一致する。
